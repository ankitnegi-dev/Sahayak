ParentBot: Complete Build Roadmap (Go)
A solo, learning-by-doing plan for a WhatsApp voice assistant that helps parents book cabs
and food in Hindi/Hinglish.
1. Project overview
What it is: A WhatsApp AI agent for parents. A parent sends a voice note like 'mere liye
cab book karo'. The bot understands it, asks short follow-up questions, confirms the
details, and completes the booking (or sends a one-tap booking link). The child sets up
saved places, spending limits and monitors activity through a web dashboard.
Why it is worth building: Parents already live on WhatsApp but struggle with Uber,
Zomato and BookMyShow (new apps, OTPs, English UI). The person who feels the pain,
the child, is the natural customer.
Your goals as a solo student:
Learn Go properly by building something real (you already know Python, so this is your
second language).
Practise production-grade engineering: idempotency, state machines, safety rules in
code, testing, observability, CI/CD.
End with a portfolio project that runs for real with your own family.
Honest scope: Production-grade engineering, not a licensed company. You will use the
WhatsApp Cloud API test number (up to 5 verified recipient numbers), start with cash or
pay-on-ride, and begin with deep links before attempting real network booking.
2. Scope: what is in and what is out
In scope (v1):
WhatsApp voice and text input in one language (your parents' language first)
Speech-to-text with a measured accuracy benchmark
Conversation engine built as a state machine
Cab flow in one city (deep link first, ONDC/Beckn sandbox second)
Saved places, spend caps, confirmation before every booking
Child dashboard (web)

4. System architecture
Request flow:
1. Parent sends a WhatsApp message. Meta calls your webhook.
2. The API verifies the signature, stores the message ID (deduplication) and pushes a job
to Redis, then returns 200 immediately.
3. A worker picks up the job. If it is a voice note, it downloads the audio and transcribes it.
4. The conversation engine loads the user's state, asks Claude to extract structured
intent, validates it, and moves the state machine.
5. The safety layer checks limits and rules.
6. If a booking is confirmed, the booking provider creates the ride (deep link or Beckn).

6. The roadmap (about 20 weeks, part-time)
Phase 0: Learn Go (Weeks 1-2, compress to 1 week if quick)
What: Learn the Go-specific differences from Python, not programming basics.
How:
Skim A Tour of Go, then work through Go by Example.

Phase 2: WhatsApp webhook (Weeks 4-5)
What: The endpoint that Meta calls for every incoming message.
How:
Create a Meta developer account and a WhatsApp Cloud API app. Use the free test
number and add up to 5 recipient numbers (family and friends).
Implement the GET verification handshake.
Implement POST handling: read the raw body, verify the X-Hub-Signature-256 header
using HMAC-SHA256 (crypto/hmac) with hmac.Equal for constant-time comparison.
Insert the WhatsApp message ID into processed_messages with a unique constraint. If
it already exists, ignore the message. This prevents duplicate bookings from Meta's
retries.
Enqueue the event to Redis with asynq and return 200 right away.
Build a small whatsapp package (net/http) for sending text replies and fetching media.
There is no official Go SDK, and the API is simple.
Use ngrok or Cloudflare Tunnel for local testing.
Tests: Valid signature, invalid signature, duplicate message, malformed JSON.
Done when: You send a WhatsApp message and see one verified, deduplicated log line,
even if Meta sends it twice.

Phase 3: Voice pipeline (Weeks 5-7)
What: Convert a voice note into text, and know how accurate it is.
How:
Fetch the media URL from the Meta API, then download the OGG/Opus audio with the
access token.
Convert with ffmpeg through os/exec if a provider needs a different format.
Define an ASR interface: Transcribe(ctx, audio) (Result, error), where Result has text,
language and confidence. Implement Sarvam, Whisper and optionally Google STT
behind it.
Record 30-50 voice notes from your parents (different rooms, speeds, background
noise). Write correct transcripts by hand.
Compute word error rate with a small Python jiwer script or your own Go edit-distance
function. Compare providers and pick the best.
If confidence is low, reply asking them to repeat instead of guessing.
Delete audio right after processing and keep only the text.
Done when: You have a benchmark table (provider, WER, latency, cost) and a chosen
default.
Phase 4: Data layer (Weeks 6-8, alongside Phase 3)
What: Reliable storage.
How:
Create the schema from section 5 using goose migrations.
Write your queries in SQL files and generate Go code with sqlc.
Use transactions for anything that changes orders and audit_log together.
Add database constraints (CHECK on status values, foreign keys, unique keys).
Tests use testcontainers-go to run a real Postgres, not mocks.
Done when: You can create a user, saved places and an order, and illegal state transitions
are rejected.

States (cab flow): idle, awaiting_pickup, awaiting_drop, awaiting_confirmation, booking,
active_ride, completed, cancelled, error.
How:
Implement states as Go constants and transitions as a table (map of state and event to
next state). A hand-written machine teaches more than a library; looplab/fsm is an
option later.
Call Claude through anthropic-sdk-go with tool use. Define tools such as
extract_ride_request returning pickup, drop and time. The model returns structured
data, never free-form decisions.
Validate every LLM output with go-playground/validator. Reject or re-ask on anything
unexpected.
Resolve ghar, mandir and similar words from saved_places. If a place is unknown, ask a
short question.
Always send a plain confirmation (pickup, drop, estimated fare) and require an explicit
haan before booking.
Handle changes of mind, cancellations, silence timeouts, and unrelated messages.
Replies are short, polite and in the parent's language. Keep a prompt file per language.
Tests: Table-driven tests for each transition, plus a set of 30+ scripted conversations
(wrong place, changed mind, abuse, gibberish, wrong language).
Done when: A voice note reaches the confirm step with correct data, and bad inputs
never skip the confirmation.
Phase 6: Safety layer (Weeks 11-12)
What: Rules in code that the AI cannot override. Elderly users are prime scam targets, so
this is the most important phase.
How:
A safety package called before every booking. It checks the per-ride cap, daily cap,
allowed hours and known places.
Unusual requests (a far destination, rapid repeated bookings, a new place) require
approval from the child over WhatsApp before proceeding.
Treat forwarded messages, links and pasted text as untrusted. Never let message
content change the system prompt or tools (prompt-injection defence).
Rate limiting per user with httprate or redis_rate.

Phase 9: Reliability (Weeks 16-17)
What: Handle failures gracefully.
How:
asynq retries with exponential backoff, timeouts, and scheduled tasks for ride-status
polling.
context deadlines on every external call.
A circuit breaker (sony/gobreaker) around ASR, LLM and provider calls.
Fallback messages, for example: kuch gadbad ho gayi, main aapke bete ko bata deta
hoon. Also notify the child.
Graceful shutdown so in-flight jobs finish during deploys.
Reconciliation job that finds orders stuck in booking and fixes or flags them.
Done when: Killing Redis, Postgres or a provider mid-flow leads to a clean retry or a clear
message, never a duplicate or lost booking.
Phase 10: Observability and security (Weeks 17-18)
What: Know when things break and close the obvious holes.
How:
sentry-go for errors, Prometheus metrics, Grafana Cloud dashboards, UptimeRobot for
uptime.
Track: booking success rate, ASR failure rate, LLM latency, p95 response time, queue
depth, safety-block count.
Redact phone numbers and addresses in logs. Add request IDs to trace one message
through all services.
Run govulncheck, gosec and Dependabot in CI.
Load test with k6 or vegeta and fix what breaks.
Secrets only in environment variables or the platform's secret store. Rotate any key
that ever touches Git.
Write a short threat model: what can a malicious message, a stolen phone or a leaked
token do?

8. Testing strategy
Unit tests: Table-driven tests for the state machine, safety rules and parsers.
Integration tests: testcontainers-go with real Postgres and Redis.
Contract tests: httptest fake servers for WhatsApp, ASR, Claude and booking
providers.
Conversation tests: A library of scripted dialogues run in CI, including adversarial
ones.
ASR benchmark: Track word error rate over time as a number in your repo.
Load and failure tests: k6 plus deliberately killing dependencies.
Coverage goal: High coverage on safety, conversation and order code; do not chase 100
percent everywhere.

10. Weekly habits
Pass context.Context as the first argument of functions that do I/O.
Wrap errors with fmt.Errorf and %w so you keep the cause.
Define interfaces where they are used, not where they are implemented.
Keep packages small and focused; avoid global state.
Write the test first for state machine and safety logic.
Update docs/decisions.md every time you choose or change something.
Commit small, merge often, and keep CI green.
